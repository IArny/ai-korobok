# 0.1.0 — 2026-11-19

First versioned release. Covers everything since `ff05080` (`origin/master`,
"fix permissions") through `7f191c0`.

This version closes the gap between "the VM exists" and "the VM is usable":
`create` waits for cloud-init, agent state survives destroy/recreate, the guest
can act as a libvirt host for nested e2e VMs, and repeated creates reuse a
cached cloud image and apt packages instead of downloading them again.

## Highlights

- **`create` only reports success when provisioning is done.** It follows the
  cloud-init steps, survives the final reboot, and re-points port forwards if
  the guest IP changes.
- **Agent state is persistent and portable.** OpenCode config, credentials, and
  sessions are synced to a host directory and can be archived/restored with
  `backup-agent` / `restore-agent`.
- **Nested e2e inside the guest.** QEMU/libvirt are installed and enabled in the
  guest, so destructive `create`/`destroy` checks can run against a throwaway VM
  instead of the user's main one.
- **Downloads happen once.** The Ubuntu cloud image is cached outside `.state/`
  and a guest `apt-cacher-ng` serves repeat nested provisions.
- **Host firewall/Docker forward fixes.** `create`/`start` repair a `DROP`
  `FORWARD` policy and persist the rules.

## Added

### Provisioning wait

- A provisioning sentinel at `/var/lib/ai-korobok/provisioned` (boot id + UTC
  timestamp), written as the final cloud-init `runcmd` step.
- `wait_for_provisioning()` in `vm.sh`: non-interactive SSH polling until the
  sentinel exists and `cloud-init status` reports `done`, tolerant of the
  post-provisioning reboot, with a bounded timeout.
- `create` progress output: the current `>>> step` from
  `/var/log/cloud-init-output.log`, elapsed time, and a clear "still
  provisioning" line instead of looking hung.
- `create --no-wait` (return after the IP/port-forward step) and
  `create --timeout <seconds>`.
- `provisioning.wait` (default `true`) and `provisioning.timeout_seconds`
  (default `1800`) in `config.json`. On timeout the VM is left running, a
  warning points at the guest log, and the command exits `0`.
- Post-reboot IP re-resolution with port forwards re-applied to the new address.
- `status` reports `starting`, `in progress (<step>)`, `complete`, or `error`;
  `ssh` warns when provisioning is still running and then connects anyway.

### Agent persistence and backups

- `opencode_persistence.*` settings: `enabled`, `host_path` (default
  `~/.local/share/ai-korobok/opencode`, mode `0700`), `backup_profile`,
  `include_cache`, `include_docker_volumes`.
- Backup profiles `minimal`, `agent` (default), and `full`; `full` adds caches
  and model weights, and Docker volumes only when enabled.
- Guest paths resolved with `opencode debug paths` (config, data, state, cache).
- Automatic sync: `create`/`start` restore, `stop`/`destroy` sync before the
  guest is lost; `destroy` leaves the host copy untouched when the VM is gone.
- `backup-agent [archive]`: syncs a running VM first, otherwise archives the
  host copy; default name `opencode-agent-<vm>-<timestamp>.tar.gz`, mode `0600`,
  gitignored.
- `restore-agent <archive> [--force]`: manifest/tar validation, refusal to
  overwrite without `--force`, ownership mapping to `ubuntu`, and an immediate
  push when the VM is running (otherwise applied on the next `create`/`start`).
- Archive manifest records format version, timestamp, source VM, OpenCode
  version, profile, and included paths; the guest `authorized_keys` is never
  synced or restored.

### LanceDB and semantic indexing

- Guest installs `lancedb` + `pyarrow`, the OpenCode v2 CLI (`@opencode/cli`),
  and the `@javierkaiser/opencode-indexing` plugin (embedded LanceDB index),
  installed for the `ubuntu` user.
- Node.js 22 from NodeSource when missing or too old.
- `install-lancedb` command for existing VMs; idempotent and safe to re-run.

### Backlog workflow skill

- `skills/backlog/SKILL.md` is embedded into cloud-init through
  `__BACKLOG_SKILL_CONTENT__` and installed at
  `/opt/opencode/skills/backlog/SKILL.md` and in the `ubuntu` user's OpenCode
  config.

### Nested e2e

- Guest packages: `qemu-system-x86`, `qemu-utils`, `libvirt-daemon-system`,
  `libvirt-clients`, `dnsmasq-base`, `cloud-image-utils`, `genisoimage`,
  `ovmf`, `jq`, `iptables`, `cpu-checker`, `apt-cacher-ng`.
- Cloud-init enables `libvirtd`, starts the default NAT network, adds `ubuntu`
  to `libvirt`/`kvm`, and warns when `vmx`/`svm` is not exposed.
- `install-e2e-deps` command and `scripts/install-e2e-deps.sh` for existing VMs.
- The setup playbook persists `kvm_intel.nested=1` / `kvm_amd.nested=1` in
  `/etc/modprobe.d/kvm-nested.conf` and reloads the module only when it is not
  busy.
- README recipe for running the e2e suite inside the guest, including disk
  placement and permission notes.

### Caching

- `cache_dir` (default `<disk dir>/cache`, e.g.
  `/var/lib/libvirt/images/cache`) stores
  `ubuntu-24.04-server-cloudimg-amd64.img`; `destroy` leaves it in place.
- Automatic migration of images left next to the disk or in `.state/`; the
  cached image is made mode `0644` so the QEMU user can read it.
- `apt_proxy` with `auto` (probe the default-network gateway on port `3142`),
  `none`/`off`/`false`/`no`, or an explicit `host[:port]`. The resulting
  `Acquire::http::Proxy` is injected into nested cloud-init.
- The guest runs `apt-cacher-ng`; apt HTTPS repositories bypass it through
  `Acquire::https::Proxy "DIRECT"`, since they are not cached anyway.
- `apt_mirror` (empty by default) overrides both the primary and security
  Ubuntu archives.

### Host networking

- `create`/`start` check the iptables `FORWARD` policy and set it to `ACCEPT`
  when needed.
- Rules are persisted with `netfilter-persistent` on Debian/Ubuntu or
  `/etc/sysconfig/iptables` on Fedora. The playbook installs
  `iptables-persistent` (non-interactively) or `iptables-services` and enables
  restore at boot.

## Changed

- `create` now waits for provisioning by default; `--no-wait` restores the old
  behavior.
- `destroy` and `stop` sync agent state before shutting down or deleting the
  disk.
- The cloud-init shared-directory block is conditional: configs without
  `shared_dir` no longer write an empty `virtiofs` fstab entry or run
  `mkdir -p` with no operand.
- The SSH hint after `create` uses the configured forward whose guest port is
  `22`, instead of hardcoding `-p 2222`.
- The TCG fallback uses `<cpu mode='maximum'>`, which libvirt 10 accepts (the
  old `max` alias is rejected).
- IP discovery waits up to 90 attempts (about 3 minutes), enough for a nested
  boot.
- Guest Python packages are reduced to `uvicorn` (the `openai`, `anthropic`,
  `httpx`, `fastapi`, and `pydantic` preinstalls were removed), and `fish` is
  added.
- Privileged steps now go through `priv()`, which runs directly as root or via
  non-interactive `sudo -n` for sudo-capable users.
- README and AGENTS document provisioning, persistence, nested e2e, caching,
  and the guest/host dependency split.

## Fixed

- Non-root `iptables` calls aborted `create` when the host `FORWARD` policy was
  `DROP`; forwarding now works for normal sudo users.
- `dnsmasq-base` was only a `Recommends` of `libvirt-daemon-system`, so the
  default NAT network could not start inside the guest.
- Nested provisioning failed on the HTTP archive with `403 CONNECT denied`
  because apt sent HTTPS through `apt-cacher-ng`; HTTPS is now direct.
- `destroy` could not remove the libvirt-chowned disk, seed ISO, or state
  directory as a non-root user.
- Port forwards kept pointing at the pre-reboot IP after cloud-init changed it.
- A `virsh net-info | grep -q` pipeline could SIGPIPE `virsh` under `pipefail`
  and report the network as inactive on installer re-runs; the output is now
  captured first.
- The installer summary used `qemu-img --version | head`, which could SIGPIPE
  under `pipefail`.

## Upgrade notes

- **Existing VMs:** recreate them to get the new guest packages, or run the
  installers: `./vm.sh install-e2e-deps` and `./vm.sh install-lancedb`.
- **New config keys are optional.** Missing `cache_dir`, `apt_proxy`,
  `apt_mirror`, `provisioning`, and `opencode_persistence` fall back to the
  defaults above. Copy the new `config.example.json` entries to customize them.
- The cloud image now lives in `cache_dir` (default `<disk dir>/cache`); a
  previously downloaded image next to the disk or in `.state/` is moved
  automatically. `destroy` no longer removes it.
- `apt_proxy: auto` only activates when the gateway answers on port 3142, so
  hosts without a local cache are unaffected. Use `"apt_proxy": "none"` to
  disable the probe explicitly.
- Agent persistence is enabled by default. The first `create` with an empty
  host persistence directory is a no-op; the directory and archives contain
  credentials and must be treated as sensitive.
- `export`/`import` still cover the disk, XML, config, and keys only; copy the
  persistence directory or a `backup-agent` archive separately.

## Known limitations

- Nested e2e needs a writable `/dev/kvm` for KVM acceleration; otherwise it
  falls back to TCG (much slower). `setup.sh` only enables nested
  virtualization best-effort when the module is not in use.
- `apt-cacher-ng` caches only HTTP archive traffic. NodeSource, Docker, and
  npm use HTTPS and are not cached.
- Agent-persistence and provisioning-UX e2e checks that need multiple VM
  lifecycles are tracked in `backlog/todo/005-TASK-verify-persistence-and-provisioning-e2e.md`.
